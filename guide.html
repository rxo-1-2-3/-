完全自動化システム構築ガイド v2（切替式）

GitHub Actions × Zoho Sheet で日経平均を自動収集する

1. このガイドの立ち位置

日々の業務や投資分析において、データを手動で集める作業は、もっとも創造性を奪う ルーチンワークの一つです。GitHub Actions と Zoho Sheet を組み合わせれば、 この作業は完全な自動パイプラインに置き換えられます。

v2 では、前版で問題になっていた「Zoho API 直書き方式」と「CSV公開方式」の混在を解消し、 環境変数1つで切り替えられる構成にしました。どちらを選んでもコードは共通です。

                                    ┌─ OUTPUT_MODE=csv ─▶ CSVをWeb公開 ─▶ Zoho Sheetが取り込む
[Yahoo Finance] ─▶ [GitHub Actions] ┤
                                    └─ OUTPUT_MODE=api ─▶ Zoho Sheet APIへ直接書き込み

2. まず決めること：どちらの方式で始めるか

ここを最初に決めないと、手順の半分が無駄になります。

csv 方式（推奨）api 方式
セットアップ時間約15分約45分
Zoho APIの登録不要必要
リフレッシュトークン発行不要必要
GitHub Secrets0個4個
リポジトリの公開設定Public必須（無料プラン）Private可
データの見え方CSVが誰でも閲覧可能非公開
Zoho側の更新頻度無料プランは1日1回書き込んだ瞬間

迷ったら csv 方式です。 株価は公開情報なので、Publicリポジトリでも実害はありません。 あとから OUTPUT_MODE を変えるだけで api 方式へ移行できます。

GitHub Pages の制約（重要） 公式ドキュメントに次の記載があります。 「GitHub Pages is available in public repositories with GitHub Free and GitHub Free for organizations, and in public and private repositories with GitHub Pro, GitHub Team, GitHub Enterprise Cloud, and GitHub Enterprise Server.」 つまり無料プランでは Public リポジトリでしか Pages を使えません。 Private のまま運用したい場合は api 方式を選んでください。

3. 各コンポーネントの役割

  • Python（取得・整形・安全弁）：通信リトライ、重複排除、欠損処理、

そして異常検知を担当します。おかしなデータを検知したら、後続に流さず処理を止めます。

  • GitHub Actions（実行・監視）：毎営業日の定刻にスクリプトを起動します。

失敗時は赤い×を灯し、Issue でお知らせします。

  • Zoho Sheet（保存・可視化）：受け取ったデータを関数で整形し、ダッシュボード化します。

4. Python 側の設計

4-1. 指数関数的バックオフによるリトライ

ネットワークの一時的な瞬断でシステムを止めないため、再試行の間隔を 1秒 → 2秒 → 4秒 → 8秒 と延ばしながら最大5回試します。 最終試行のあとには待機を入れません。 どうせ諦めるのに待つのは無駄だからです。

4-2. 安全弁としての sys.exit(1)

取得データの形式が想定と違う場合、無理に処理を継続してはいけません。 異常を検知したら sys.exit(1) を返し、GitHub Actions に「失敗」を伝えてその場で止めます。 汚れたデータが Zoho Sheet に書き込まれるのを防ぐ、文字どおりの安全弁です。

4-3. バリデーションは「固定上限」ではなく「前日比」で

前版は 終値 > 100000 なら異常、という固定上限で判定していました。 これは指数が長期的に上昇するといずれ必ず誤検知します。

v2 では前日比の変動率で判定します（既定は ±20%)。 桁ズレや単位変更のようなデータ破損は確実に捕捉でき、かつ将来の水準上昇では誤検知しません。

前日 42,000 → 当日 4,250（1/10に桁ズレ）  → 変動率 89.9% → 停止
前日 42,000 → 当日 45,000（通常の上昇）    → 変動率  7.1% → 通過

4-4. 営業日判定

土日、日本の祝日（jpholiday）、そして年末年始（12/31〜1/3）を休場と判定し、 早期終了します。GitHub Actions の無料実行枠を無駄遣いしないための工夫です。

前版はこの年末年始の判定が [1, 16, 24] になっており、 1月16日・24日という実際の取引日を毎年スキップしていました。 v2 では [1, 2, 3] に修正し、自己テストで固定しています。

5. GitHub Actions 側の設計

5-1. UTC と JST の時差（cron 設定）

cron は世界標準時（UTC）で動きます。日本時間から9時間引いて指定します。

  • cron: '30 7 * * 1-5' → UTC 7:30 = JST 16:30（東証の取引終了後、平日のみ）
  • JST 9:00 に動かしたいなら → cron: '0 0 * * 1-5'

5-2. dry_run を「本当に」配線する

前版は workflow_dispatch に dry_run を宣言していましたが、 実行ステップがその値を一切参照していませんでした。 つまり true にしても本番実行され、CSVがコミットされていました。

v2 では入力値を実際にコマンドライン引数へ渡します。

run: |
  ARGS=""
  if [ "${{ inputs.dry_run }}" = "true" ]; then ARGS="$ARGS --dry-run"; fi
  if [ "${{ inputs.force }}"   = "true" ]; then ARGS="$ARGS --force"; fi
  python fetch_and_push.py $ARGS

スケジュール起動時は inputs が空になるため、引数なし（＝本番実行）になります。

5-3. 休場日に「誤報」を出さない

前版には次の落とし穴がありました。休場日は Python が CSV を作らずに終了するのに、 コミットステップは動いてしまい、git add が存在しないファイルを掴んで exit 128 で失敗 → 「🚨 システム警告」Issue が誤発報していました。 セットアップ直後の初回が祝日だと、いきなり真っ赤になります。

v2 では三重にガードしています。

  1. Python が休場日に skipped=true を GITHUB_OUTPUT へ出力し、後続ステップが自分でスキップ
  2. コミットステップの冒頭で CSV の存在を確認し、無ければ正常終了
  3. ヘッダーのみの CSV を最初から同梱し、初回でも git add が失敗しない

5-4. Issue を増殖させない

失敗のたびに新規 Issue を立てると、連日失敗した場合に埋め尽くされます。 v2 は未解決の同種 Issue を検索し、あればコメントを追記するだけにします。

6. Zoho Sheet 側の連携

6-1. IMPORTDATA は使えません

IMPORTDATA は Google Sheets の関数で、Zoho Sheet には存在しません。 Zoho Sheet にあるのは IMPORTRANGE ですが、これは Zoho Sheet 同士の連携専用で、 外部URLのCSVは読めません。

外部CSVの取り込みには、必ず「データ」→「データ接続」機能を使ってください。 URL を指定し、更新頻度を選ぶだけです。無料プランは1日1回、有料プランなら1時間ごとに更新できます （どちらも24時間で最大50回まで）。

6-2. ヘッダーは手入力しない

csv 方式では、データ接続が CSV の1行目（Date,Close,Volume）を そのままヘッダーとして展開します。事前に手入力しておくと、 上書きされるか範囲の衝突エラーになります。

6-3. 見た目を整えるクレンジング関数

このパイプラインは生データをそのまま渡す設計です。 表示用の整形はシート側の役割として分離してあります。 こうしておくと、将来データソースを変えても集計ロジックが壊れません。

関数用途実例
SUBSTITUTE不要な文字の置換SUBSTITUTE("2017.01.04",".","/") → 2017/01/04
VALUE数値型への変換VALUE("19,594.00") → 19594
DATEVALUE日付型への統一DATEVALUE(A1) → シリアル値（グラフ描画に必須）
IFERROR取得失敗時の回避IFERROR(式,"確認中") → 表示崩れを防止

単位の正規化：出来高は株数（例 2,375,713）で入ります。 グラフに載せると桁が多すぎるので、表示用の列で =A1/1000 として 「千株」に正規化すると読みやすくなります。

7. セットアップ手順の要約

csv 方式（約15分）

  1. コード一式を Public リポジトリにアップロードし、Actions を有効化
  2. Settings → Pages → Branch main / フォルダ /docs で公開
  3. Actions から手動実行（dry_run=true → 確認 → false で本番）
  4. 公開ページに出る CSV の URL を、Zoho Sheet の「データ接続」に貼る

api 方式（約45分）

上記1に加えて、Zoho API コンソールでアプリ登録 → get_zoho_refresh_token.py で 鍵を発行 → Secrets 4つと Variables を登録 → OUTPUT_MODE=api に設定します。

データセンターの選択に注意。日本のアカウントは https://accounts.zoho.jp です （.co.jp ではありません）。

クリック単位の詳細手順は、コード一式に同梱の README.md にあります。

9. 自分で確かめられること

セットアップ前でも、ネットワーク接続なしでロジックの正しさを検証できます。

python tests/test_pipeline.py

休場判定・年末年始・重複排除・欠損処理・安全弁・モード切替の26項目を検証します。 GitHub Actions 上でもデータ取得の前に毎回実行されるので、 コードを書き換えて壊した場合はその場で気づけます。

10. おわりに

自動化システムは「完成」がゴールではありません。市場環境や技術スタックの変化に合わせて、 少しずつ調整して育てていくものです。

そのとき効いてくるのが、sys.exit(1) による安全停止、失敗時の自動通知、 そして自己テストです。テストがあると、手を入れて壊したときにすぐ気づけます。 安心して触れる状態を保つことが、長く動かし続けるための一番の近道です。
